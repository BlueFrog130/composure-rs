# A Theme on the Command Set fills in Responses, never overrides them

Bots want every embed they answer with to look the same: one color scheme, the same author and footer. A `Theme` is a `const` value (semantic colors as plain `u32`, branding as `&'static str`, so it costs nothing at runtime) set on the Command Set with `commands! { ...; theme = THEME; }`; it is exposed as `InteractionHandler::theme()` (default `None`, `WithFallback` passes the set's on) and reaches handlers as `ctx.theme()` on every Ctx, including `DeferredCtx`, by threading it through `Invocation` and the Component/Modal Handler `invoke` (which now take a Ctx). A per-request Theme (e.g. per-guild colors from storage) was rejected: it would need State the framework does not own, and users can build it on the `Embed` builders. `dispatch` applies the Theme to message Responses (types 4 and 7) and deferred Background Work applies it before editing the original: it only fills fields that are `None` (color on every embed, author on the first, footer on the last, `primary` as `accent_color` of top-level Components V2 Containers), so anything set explicitly wins, and `Unthemed(response)` opts a message out entirely through a skipped flag on `MessageCallbackData`. Errors become an ephemeral `error`-colored embed via `HandlerError::response_with(theme)`, which Adapters call with the handler's Theme; without a Theme everything is answered exactly as before. Messages sent through REST (follow-ups, `create_message`, webhooks) are never rewritten, since their bodies are built by the user; the `Theme::success`/`error`/... helpers produce branded embeds for them.
