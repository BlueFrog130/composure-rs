# Views render from Props; inline handlers are named and capture only Props

Layout built from `types::Component` constructors is verbose, and the handlers for its buttons live far from the markup. `#[view] fn Card(title: String, likes: u32) -> View` with a JSX `rsx! { .. }` body (parsed with `rstml`, as leptos does; the markup macro is `rsx!` because an attribute and a bang macro cannot share the name `view`) gives a leptos-like way to write it, but without signals or any other reactivity: Discord keeps no client state, so each click is a new Interaction, and the only state that survives is the 100-char `custom_id` (ADR 0007). A View is a pure function of its Props. `#[view]` generates a same-named Props struct, and a handler re-renders by returning new Props, which answers as an `Update`. Inline handlers (`on:click:like=move |ctx| Card { likes: likes + 1, title }`) are hoisted into one Component/Modal Handler per View. Their ids are `view:handler:state` so the existing split-at-`:` routing applies. The macro has no type information, so a handler can capture only Props, never loop variables: per-row state means extracting a sub-View. Of those Props, only the ones the closure body names syntactically get encoded, which keeps ids short. Handlers must be named. Positional ids were rejected because messages that were already sent keep their ids across deploys, and reordering the markup would silently route old buttons to the wrong handler with wrongly decoded state. A removed name falls through to the fallback like any unknown prefix. Views with handlers are listed explicitly in `commands! { views = [..] }` (ADR 0001), and `commands!` checks at compile time that sub-Views with handlers are registered. Message Views always answer as Components V2. A `<Modal>`-rooted View answers as a modal, and its typed submit parameters reuse `ModalValue`, so they agree with `derive(Modal)`. `rsx!` expands to `types::*` literals with no runtime tree, and `custom_id` errors are carried inside `View` and surface as a `HandlerError` at response time.
