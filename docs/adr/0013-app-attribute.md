# An App is an `#[app]` attribute on a unit struct, listing one kind of thing: Routes

`commands! { pub struct Bot = [..]; components = [..]; modals = [..]; views = [..]; theme = ..; events = ..; }` outgrew its name and its shape: it registers components, modals, Views, a Theme and Webhook Events too; its `struct Bot = [..]` head looks like nothing else in the framework, where every other piece is an attribute on an item (`#[command(..)]`, `#[group(subcommands(..))]`, `#[component("p")]`, `#[view]`); `macro_rules!` fixes the order of its keys; users must sort each handler into the right list, though a View is both a component and a modal handler; and one flat list at the crate root sits far from the modules defining what it lists. It is replaced by `#[app(handlers(..), theme = THEME, events = Events)] pub struct Bot;`, a proc macro in `composure_macros` (so it needs the `macros` feature, which every bot written with `#[command]` already has). Everything it lists is a Route: `#[command]`, `#[group]`, `#[component]`, `#[modal]`, `#[view]` and `#[app]` itself implement `RouteDefinition` (`const ROUTE: RouteInfo`, one of Command `{name, kind, scope}`, Component `{prefix}`, Modal `{prefix}`, View(`ViewInfo`), App `{routes, events}`; an App's `THEME`; its Command Definitions for Sync) and `Route<S>` (replacing `CommandSet<S>`), whose `dispatch`/`dispatch_autocomplete`/`dispatch_component`/`dispatch_modal`/`dispatch_event` default to `None` (or ignoring the event), so each kind overrides what it answers through small `command::__dispatch_*` helpers. An App chains its children's, so dispatch stays static and inlines to the same `if` chain `commands!` generated. The compile-time checks (duplicate Commands, per-Scope limits, prefix collisions, unregistered sub-Views) become const fns walking the `RouteInfo` tree in a `const _` the macro emits for each App, so they run before monomorphization and `cargo check` reports them. Because an App is a Route, Apps nest: a module declares `#[app(handlers(counter, counter_click))] pub struct Interactive;` next to its handlers and the root lists `Interactive`; registration stays explicit (ADR 0001), only closer to the code. A nested App's `theme` cascades: its Routes see it in `ctx.theme()` and its responses are filled from it first, then from the Apps around it; errors are rendered by the Adapter with the outermost App's. At most one App in a tree sets `events` (two is a compile error, since a bot has one events URL), and the root hands Webhook Events to it wherever it is nested, so a shared App can carry the events into every platform's App that lists it. `#[diagnostic::on_unimplemented]` on `RouteDefinition` explains a listed path that is none of the above. `with_fallback`, `InteractionHandler`, `EventHandler` and `CommandSetDefinition` (for Sync) are generated as before. The name is App, after Discord's application, because `bot` already means the Bot Client (`ctx.bot()`); the glossary's Command Set becomes App. Rejected: a bang macro with struct-literal keys (`app! { pub struct Bot { handlers: [..], theme: THEME } }`), whose keys could come in any order but whose syntax would still be its own and unformatted by rustfmt; and a plain trait impl (`impl App for Bot { type Routes = (..); const THEME: .. }`), whose tuples cap the number of Routes and whose checks would fire only after monomorphization, so `cargo check` would miss them.
