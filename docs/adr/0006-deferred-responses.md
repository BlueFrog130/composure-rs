# Deferred Responses hand Background Work to the Adapter

A Command that needs more than Discord's 3-second window returns `ctx.defer(async |ctx| ..)` (wrapped in `Ephemeral` to defer ephemerally), whose closure receives a `DeferredCtx`. `defer` needs the State to implement `Platform`: the Adapter's hook for a REST Transport, the bot token, and `spawn`, which runs Background Work after the response is sent (`wait_until` on Cloudflare). `defer` builds the work (run the closure, then edit the original response with its output, or with the Handler error message on failure), hands it to `spawn`, and returns the type 5 reply. Going through the State keeps dispatch, `InteractionHandler`, and the macros' return types unchanged; the alternative, returning the work alongside the response from dispatch, would have changed every handler signature. The hot path keeps the borrow-only `Ctx<'a>`; only deferred work pays for owning a copy of the Interaction (`Rc`) and State (`Platform: Clone`). Ephemerality is chosen at defer time because Discord fixes it on the deferred reply. Background Work can start before the platform finishes sending the reply, so the final edit retries briefly while Discord reports the response unknown (404). Background Work is bounded by the platform (about 30s on Workers) even though the interaction token lasts 15 minutes; longer jobs are out of scope. The same hook will ACK Webhook Events (0008). Initial responses carrying files are sent by the Adapter through the callback endpoint as multipart, answering the original request with 202. Since 0012 the Interaction is shared through `Arc` and Background Work is `Send`, so a hosted server runs it with `tokio::spawn`, bounded by its shutdown grace period instead.
