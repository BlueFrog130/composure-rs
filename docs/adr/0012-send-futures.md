# Core futures are `Send`; Workers bridges JS with `SendWrapper`

A hosted server (the tokio Adapter) wants each Interaction on its own `tokio::spawn`ed task, work-stealing across cores, and handlers that can move a ctx into tasks of their own. That needs handler futures to be `Send`, and since return type notation (`H::method(..): Send`) is still unstable, generic code (dispatch, `defer`, `spawn_event`, the Adapters) can only know that if the traits say so. So every handler trait (`InteractionHandler`, `Command`, `CommandSet`, `ComponentHandler`, `ModalHandler`, `ViewHandler`, `Autocomplete`, `EventHandler`) and `Transport` declare `fn .. -> impl Future<Output = ..> + Send` (impls still write `async fn`), `Ctx`/`DeferredCtx`/dispatch share the Interaction through `Arc`, `Lazy` uses `OnceLock`, `BackgroundWork` is `Send`, and `Platform` is `Send + Sync`. The cost lands on Workers, which is single-threaded: `Worker` wraps `Env`/`Context` in `worker::send::SendWrapper`, `FetchTransport` wraps its fetch in `SendFuture`, and handlers that await JS futures (KV, D1, ...) need `#[worker::send]` or `SendFuture`. The alternatives were a single-threaded tokio Adapter (one core), pinning each Interaction to a `LocalPoolHandle` worker (parallel, but nothing an Interaction owns can cross threads), or a `send` cargo feature (it adds bounds, so it is not additive, and features unify across a workspace). Atomics instead of plain counters cost nothing measurable per request.
