# Instrumentation through `tracing`, opt-in, subscriber in the Adapter

Composure records what it does with [`tracing`](https://docs.rs/tracing) spans and events and, as a library, never installs a subscriber. Core's `tracing` feature turns it on; without it, internal macros (`crate::trace`) expand to nothing and the dependency is not compiled, so call sites need no `cfg` and the default bundle is unchanged. Spans carry what is useful to filter logs by: `interaction` around every `dispatch` (id, type, command name or `custom_id` prefix, guild, user; never the token or `custom_id` state), `background_work` for deferred completions and `event` for Webhook Events (both entered while calling `Platform::spawn` and instrumenting the work, so Background Work logs keep the Interaction's context), and `rest` per Endpoint call (method and route template, not the URL, which can hold an Interaction token). REST responses and rate-limit waits are DEBUG, giving up on a rate limit WARN. Handler errors are logged by core inside the span they happened in (`HandlerError::trace`: ERROR for failures, WARN for unknown commands and invalid Options, DEBUG for user errors), since the Adapter only sees them after `dispatch` returns, outside the `interaction` span; with `tracing` the Adapter does not log them again. The Cloudflare Adapter's `tracing` feature enables core's, logs its own messages through `tracing` (straight to the console without it), and ships a minimal `tracing-subscriber` layer that writes each event as a JS object to the matching `console` method, merging span fields in, so Workers Logs indexes them; applications install it from `#[event(start)]`. It is opt-in because it costs about 96 KB of wasm in the example bot (36 KB core instrumentation, the rest the registry and layer); `tracing-subscriber`'s `fmt` layer was rejected as larger and writing strings Workers Logs does not index.
