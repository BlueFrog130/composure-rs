# The Dev Loop: an installed `cargo composure dev` driving the bot's own Sync bin

composure-js's `vite dev` serves the bot, opens a tunnel, points the Dev Application at it and keeps guild Commands synced. Composure wants the same loop, but Rust changes its shape in three ways. Definitions only exist compiled into the bot, so nothing can read them without a build (Vite's `runnerImport` has no equivalent). There is no hot reload, so every save is a rebuild and a restart. And Windows can't overwrite a running exe, so a supervisor inside the crate being rebuilt fights cargo. `cargo-composure` is therefore a separate installed crate, run as `cargo composure dev`, and its interface with a bot is what every bot already has: the Sync bin's command line (`--guild <id> --yes --color never`), which it reads the outcome of. It depends on no bot and needs no new protocol, and version skew is limited to those flags. It covers both platforms, picking Workers when the package has a `wrangler.toml`.

Settings live in `[package.metadata.composure.dev]`, committed: `application`, `guild`, `tunnel`, plus `bin`, `sync_bin`, `port`, `wrangler_env`. Flags override the two ids for a developer with their own application. `DISCORD_APPLICATION_ID` can't be the safeguard, because it sits in `.env` beside the token, so a production `.env` would match itself. The Dev Application is named apart from the token, and the tool writes to Discord only when the token's application is that one: neither Repoint nor dev Sync runs otherwise, and the endpoint to set by hand is printed. That is stricter than composure-js, which still syncs. Secrets are read from `.env` under the process environment, and Workers bots move from `.dev.vars` to one `.env`: Wrangler reads `.env` when no `.dev.vars` exists, the Sync bin already reads it, and the tool warns when a `.dev.vars` would hide it.

**Repoint and the quick tunnel** port ADR 0031 of composure-js as it stands, because the race it measured is Discord's and cloudflared's, not Node's: a lookup of the hostname before the authoritative nameservers publish it caches NXDOMAIN for 60 s, at Discord too. So a quick tunnel is ready after cloudflared's first registered connection and an A record from the zone's own nameservers, and the probe (an unsigned POST expecting 401) is pinned to that IP. 429s are waited out in full, a 400 compares `verify_key` with `DISCORD_PUBLIC_KEY` and retries once after 65 s, and the endpoint isn't restored on exit. `event_webhooks_url` follows only when the application already has one, since that value can only be a dead tunnel. DNS is a small hand-written query rather than a resolver crate, to keep `cargo install` light. v1 has `"quick"`, `{ url }` and `false`; named tunnels add token handling and can come later.

**Rebuilds** are one pipeline the tool owns on both platforms: debounce saves, build, swap, then sync. Sync comes after the swap so a new Command never appears before the bot can answer it, and it runs in the background, because on Workers it means a native build of the bot on top of the wasm one (6 s against 3 to 4 s on the example). Requests made during a run collapse into one follow-up. On Workers the tool takes the project's `[build] command`, keeping it the one place that pins `worker-build`, swaps `--release` for `--dev` (3 to 4 s a save against 11 to 12 s), and runs `wrangler dev` on a generated config with `[build]` removed, next to the real one so its relative paths still resolve. Wrangler reloads when the build output changes, and a `--dev` build runs on workerd; both were checked before building on them. Left alone, Wrangler would rebuild in release, watch only its own directory (missing path dependencies) and race the tool's watcher. On a server the tool runs a copy of the exe from `target/composure-dev/`, so the old bot serves through the build and cargo can overwrite the original. A failed build leaves the last good bot serving. A swap is a hard kill and a spawn: Interactions in the gap fail and Background Work is dropped, which is acceptable in development. Sync's bin is built by its own `cargo run`, never by the server's build, so cargo never overwrites it while it runs.

The watcher covers every local package reachable through normal and build dependencies (`cargo metadata`): their `src/`, `Cargo.toml` and `build.rs`, plus the bot's `.env`, which restarts it even when the build didn't change. Tests drive each stage through a seam: `Transport` (`MockTransport`), `Dns`, `Probe` and `Runtime`; the real processes and Discord were exercised by hand.

Rejected:
- A `dev` bin in each bot calling a `composure_sync::dev`: no install and a pinned version, like the Vite plugin, but the supervisor lives in the crate it rebuilds, so the watcher must avoid rebuilding itself on Windows.
- Letting `wrangler dev` own the Worker's rebuilds: slow release builds, and blind to path dependencies.
- A pinned cloudflared download with checksums, as composure-js has: a checksum table and a bump script for a tool that already asks for a `cargo install`. `CLOUDFLARED_PATH`, then `PATH`, then an error with the install link. It can be added later without breaking anything.
- Blocking the swap on Sync: the bot would wait 6 s for Commands that usually didn't change.
- Skipping Sync when Definitions didn't change: that needs the same build, and an unchanged Sync is one GET.
- A TUI: bot logs and compiler errors pass through untouched, with one `[composure]` line per stage.
